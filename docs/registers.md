# Registers of the demo build

The CPU of the demo build (a [LiteX](https://github.com/enjoy-digital/litex) SoC with a
[VexRiscv](https://github.com/SpinalHDL/VexRiscv), [`tt_harness/soc/core.py`](../tt_harness/soc/core.py))
controls the project and reads the harness blocks through the CSR modules `slot`, `gamepad`,
`vga`, `sevenseg`, `atspeed` and `info`. The blocks behind them are
[`slot.py`](../tt_harness/core/slot.py), [`gamepad.py`](../tt_harness/core/gamepad.py),
[`vga.py`](../tt_harness/core/vga.py), [`sevenseg.py`](../tt_harness/core/sevenseg.py) and
[`atspeed.py`](../tt_harness/core/atspeed.py). Firmware uses the accessors LiteX generates in
`csr.h`; the addresses below are those of the reference configuration and do not move between
boards (the six modules have fixed CSR locations, `CSR_LOCATIONS`).

The first part of this page is written by hand. The CSR map after it is generated by
[`tt_harness/soc/registers.py`](../tt_harness/soc/registers.py) and checked by
`test_csr_map_is_documented_and_current` in [`tests/test_soc.py`](../tests/test_soc.py), which
fails when it is stale. Regenerate it with:

```sh
uv run python -m tt_harness.soc.registers
```

## Rules for firmware

- Reset the design after any at-speed abort, and after every finished check: a check drives
  the design with the reference stimulus, and an abort can leave one cut block (reset low from
  its first clock, then released) at the pins. The design's state afterwards is not the
  firmware's.
- Never start an at-speed check unless `clock_running` (in `slot_status`) reads 1. With the
  project clock stopped a start waits for the clock, and with `clock_hz` 0 it never runs;
  `atspeed_control.abort` recovers a check that cannot finish.
- The last start wins: a start cancels any earlier one, and only its result is reported
  (`atspeed_status.done` with `atspeed_crc`).
- With `clock_hz` 0 nothing waits on the project clock: every register write completes, reset
  is asserted at once, `slot_status` reads 0, the VGA registers read "no signal" and the
  seven-segment duty reads 0. No register access ever waits for the project domain.

## How the controls behave

- The slot's controls (`slot_ena`, `slot_rst_n`, `slot_ui_in`, `gamepad_enable`,
  `gamepad_buttons`, `slot_clock_enable`) are levels; there are no strobes. Write `ena`,
  `ui_in` and `gamepad_enable` first and release `rst_n` last: the release carries the values
  written before it, and the design sees `rst_n` high 6 to 9 project clocks after the write.
  `gamepad_buttons` is not ordered against the release.
- The VGA timing registers hold one publication of the measurement. Read `vga_frames` before
  and after the others; when it has not changed, they all belong to the same frame. With the
  project clock stopped they keep the last publication: check `clock_running`.
- The capture settings (`vga_divider` to `vga_blank`) reach the capture together, as one
  word. The capture is also blanked while `no_signal` is set, without the firmware.
- `clock_running` reads 1 for a project clock of 1 MHz and up, and flickers below about
  0.39 MHz.

## The firmware

The demo build runs [`firmware/`](../firmware) from the ROM, in place of LiteX's BIOS:
[`tt_harness/soc/firmware.py`](../tt_harness/soc/firmware.py) (`FirmwareBuilder`) builds it
as a LiteX software package with the [RISC-V GCC](toolchains.md) and loads the image into
the ROM. The simulation ([`tt_harness/soc/sim.py`](../tt_harness/soc/sim.py)) and the board
builds use it the same way. At boot it

1. puts the slot in its power-up state: `ena` 0, `rst_n` 0, clock stopped, no gamepad, capture
   blanked;
2. checks the embedded `demo.json` ([`demo_parse.c`](../firmware/demo_parse.c), the messages of
   [`tt_harness/demo/validate.py`](../tt_harness/demo/validate.py) byte for byte) and the
   build's own conditions (one project; its `clock_hz` is the slot's);
3. runs it with the demo board's runner ([`runner.c`](../firmware/runner.c),
   [`docs/demo-runner.md`](demo-runner.md)): the selection writes `ena`, the clock and `ui_in`
   (and the first steps), then `rst_n` is released once;
4. reports the clock, classifies the VGA mode from the measured counters once `locked`
   ([`vga_mode.c`](../firmware/vga_mode.c), the C form of `vga.classify`) and programs the
   capture with it.

| Memory | Holds |
| --- | --- |
| `rom` (32 KiB) | code, read-only data, the initial values of data |
| `main_ram` (64 KiB) | data, bss: the parsed demo, the parser's tokens, the console ring |
| `sram` (8 KiB) | the stack |

### Console

The UART (115200 baud) carries one line per event: a word, then `key=value` fields separated
by spaces. Lines are queued in a 4 KiB ring and sent from the main loop, so logging does not
delay the slot writes; a full ring waits, and no line is dropped. `t_ms` is milliseconds since
boot.

| Line | Field | Value |
| --- | --- | --- |
| `boot` | `project` | `<shuttle>/<macro>` |
| `boot` | `sys_hz` | system clock in Hz |
| `boot` | `clock_hz` | `info_clock_hz` |
| `boot` | `fb_width` | `info_fb_width` |
| `boot` | `fb_height` | `info_fb_height` |
| `boot` | `demo_json_bytes` | size of the embedded file |
| `demo ok` | `projects` | number of projects |
| `demo ok` | `steps` | number of steps, all projects |
| `demo error` | `count` | number of `error msg=` lines after it |
| `error msg=` | rest of the line | one message, `\` and control characters escaped as `\\`, `\n`, `\r`, `\xNN` |
| `error display` | `t_ms` | time of the blink |
| `error display` | `ena` | `slot_ena` read back |
| `error display` | `rst_n` | `slot_rst_n` read back |
| `error display` | `clock_enable` | `slot_clock_enable` read back |
| `error display` | `ui_in` | `slot_ui_in` read back, decimal |
| `state` | `t_ms` | time of the runner's event |
| `state` | `entry` | index of the selected project |
| `state` | `address` | its address |
| `state` | `subtile` | its subtile |
| `state` | `ena` | `1` |
| `state` | `clock_hz` | the requested clock |
| `state` | `ui_in` | the written value, decimal |
| `state` | `gamepad` | the report word, `0x` and six hex digits |
| `state` | `rst_n` | the written level |
| `state` | `source` | `enable`, on the one release after the selection |
| `clock` | `t_ms` | time of the change |
| `clock` | `hz` | `info_clock_hz` |
| `clock` | `achieved_num` | `info_clock_hz_num` |
| `clock` | `achieved_den` | `info_clock_hz_den` |
| `clock` | `locked` | `slot_status.locked` |
| `clock` | `running` | `slot_status.clock_running` |
| `mode` | `t_ms` | time of the change |
| `mode` | `status` | `ok`, `unknown` or `no_signal` |
| `mode` | `name` | the table's row, such as `640x480@60` (`ok` only) |
| `mode` | `refresh_hz` | `clock_hz / (clocks_per_line * lines_per_frame)`, one decimal (`ok` only) |
| `mode` | `divider` | `vga_divider` written (`ok` only) |
| `mode` | `h_offset` | `vga_h_offset` written (`ok` only) |
| `mode` | `v_offset` | `vga_v_offset` written (`ok` only) |
| `mode` | `h_step` | `vga_h_step` written (`ok` only) |
| `mode` | `v_step` | `vga_v_step` written (`ok` only) |
| `mode` | `clocks_per_line` | measured (not `no_signal`) |
| `mode` | `lines_per_frame` | measured (not `no_signal`) |
| `mode` | `hsync_width` | measured (not `no_signal`) |
| `mode` | `vsync_lines` | measured (not `no_signal`) |
| `mode` | `hsync_positive` | `vga_status.hsync_positive` (not `no_signal`) |
| `mode` | `vsync_positive` | `vga_status.vsync_positive` (not `no_signal`) |
| `fb` | `t_ms` | time of the readout |
| `fb` | `frames` | `vga_frames` |
| `fb` | `pixels` | `addr:RR` pairs joined by `,`, two hex digits each (`vga_readback_data`) |

- A `clock` line is printed for the first status and then for each change that has held 50 ms
  (`clock_running` flickers for a slow clock).
- A `mode` line is printed for each change of the measurement once it is `locked`, or when the
  signal is lost. `unknown` blanks the capture (`vga_blank` 1).
- `fb` lines are printed every 20 ms, and only in builds given framebuffer probes
  (`sim.run(fb_probes=...)`).
- The `state` lines are the runner's writes in its order; the `gamepad` word is player 1 in
  bits 23..12 and player 2 in bits 11..0 (`0xfff` absent), as `gamepad_buttons`.

### The error pattern

On an invalid `demo.json`, or one this build cannot run, the firmware prints `demo error` and
every message, never enables the project, and from then on holds it with `ena` 0, `rst_n` 0
and the clock stopped, writing `SEVENSEG_ERROR_PATTERN` to `slot_ui_in` and 0 in turn every
250 ms (one `error display` line each).

| Constant | Value | Shows |
| --- | --- | --- |
| `SEVENSEG_ERROR_PATTERN` ([`main.c`](../firmware/main.c)) | `0x79` | `E`: segments a, d, e, f, g |

#### `slot_ena`

The project's `ena` (1: enabled). A level.

#### `slot_rst_n`

The project's `rst_n` (0: in reset; 1: released). A level. Reset is asserted at once, with or without a project clock, and released on a project clock edge 6 to 9 project clocks after the write, carrying the `ena`, `ui_in` and `gamepad_enable` written before it.

#### `slot_ui_in`

The project's `ui_in`. A level. Bits 6:4 come from the gamepad emulator instead while `gamepad_enable` is set.

#### `slot_clock_enable`

1: the project clock runs (the BUFGCE enable); 0: it is stopped.

#### `slot_status`

Project clock status.

| Field | Bits | Access | Reset |
|---|---|---|---|
| `locked` | 0 | read-only | - |
| `clock_running` | 1 | read-only | - |

- `locked`: The MMCM is locked.
- `clock_running`: The project clock has been seen running in the last 512 system clocks (reads 1 for a clock of 1 MHz and up; flickers below about 0.39 MHz).

### `gamepad`

| Register | Address | Words | Bits | Access | Reset |
|---|---|---|---|---|---|
| `gamepad_enable` | `0xf0008800` | 1 | 1 | read-write | `0x0` |
| `gamepad_buttons` | `0xf0008804` | 1 | 24 | read-write | `0xffffff` |

#### `gamepad_enable`

1: the gamepad emulator drives `ui_in[6:4]` (latch, clock, data). A level, delivered with the slot's control word, so it is in place at the release.

#### `gamepad_buttons`

The 24 bits each gamepad frame sends, bit n sent n-th (`tt_harness.demo.validate.gamepad_bits`): bits 23:12 the first controller, 11:0 the second, a held button 1, an empty socket all ones. A level, not ordered against the release; the reset value is no controller.

#### `vga_clocks_per_line`

Measured project clocks from one hsync leading edge to the next.

#### `vga_lines_per_frame`

Measured lines per frame.

#### `vga_hsync_width`

Measured project clocks hsync is active.

#### `vga_vsync_lines`

Measured lines vsync is active.

#### `vga_status`

Sync polarity and lock of the measured timing.

| Field | Bits | Access | Reset |
|---|---|---|---|
| `hsync_positive` | 0 | read-only | - |
| `vsync_positive` | 1 | read-only | - |
| `locked` | 2 | read-only | - |
| `no_signal` | 3 | read-only | - |

- `hsync_positive`: hsync is active high.
- `vsync_positive`: vsync is active high.
- `locked`: The last two publications were the same timing.
- `no_signal`: No vsync within 2**23 project clocks, or none yet: the measurements are stale and the capture is blanked.

#### `vga_frames`

Publications of the timing so far, wrapping. Every timing register holds the same publication: read `frames` before and after the others.

#### `vga_divider`

Capture: project clocks per pixel (0 is 1).

#### `vga_h_offset`

Capture: project clocks from the hsync leading edge to the first pixel (0 is 1).

#### `vga_v_offset`

Capture: lines from the vsync leading edge to the first row (0 is 1).

#### `vga_h_step`

Capture: store every n-th pixel of a row (0 is 1).

#### `vga_v_step`

Capture: store every n-th row (0 is 1).

#### `vga_blank`

Capture: write the picture as black; setting it clears the buffer.

#### `vga_readback_addr`

Framebuffer pixel to read: y * 320 + x, 0 to 76799.

#### `vga_readback_data`

The pixel at `readback_addr`, valid one system clock after the address is written. No tearing protection: a pixel being captured may be new.

|---|---|---|---|
| `b` | 1:0 | read-only | - |
| `g` | 3:2 | read-only | - |
| `r` | 5:4 | read-only | - |

- `b`: Blue, 0 to 3.
- `g`: Green, 0 to 3.
- `r`: Red, 0 to 3.
